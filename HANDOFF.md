## Decoded protocol (facts from the fixed 32-bit disassembly unless marked "inferred")

1. **Error 0x45** = string "Compare bin and model name is fail". Wine fails because every NVAPI read returns junk (NVAPI absent on Linux). Not a Wine-tuning problem.
2. **Version channel (live-proven)**: vendor DDC/CC packet `0x6E 0x51 0x84 0x01 FE E1 E6` (addr/src/len/opcode/data + XOR checksum). Opcode `0x01` + 3-byte reg → 4-byte ASCII reply. Address ladder: only `FE E1 E6` is real (FW string); other addresses reply with canned `FW.0`; `FE E1 A4` = build code. Write-opcode candidates `02 03 04 32 33 3B 00` **all rejected**.
3. **ISP entry (live-proven, DP at user-level and RM-root)**: raw magic-byte writes to 8-bit `0x6F` (= 7-bit `0x37`). Candidate table (6×3B, extracted): `94 96 6a | 64 64 68 | 54 56 58 | 98 9a 68 | 9c 9e 6c | 90 92 60`. Status poll from `0x6F`; **bit 0x80 = ISP ready** (`0x0a→0xca/0xdf/0x88`). Exit = `0x24`. Flaky across runs → use full-candidate retries + INI pacing (3000 ms after DDC writes).
4. **Flash dataplane**: `IspFlash`/`DumpFlash`/`ReadFlashData` (plugin RVA `0x7e50`) contain **no DDC packet opcodes** — 32-byte pages through Comm vtable `I2C_READ`/`I2C_WRITE` → `Comm_Aux.dll` → **NVAPI `ctlAUXAccess` / `NvAPI_I2CRead`/`Write`** (dynamically resolved; `nvapi.dll` not in static imports). Code slave constants are 8-bit: `0x44`→7-bit `0x22` (MCU register file), `0x41`→`0x20`, `0x6E/0x6F`→`0x37`. Register-write primitive = 4-byte I2C-memory packet **`[reg, val>>16, val>>8, val]`** to `0x22` (`Write32BitRegEx` decode).
5. **Flash.dat** (layout refined session 14f): per-chip table records = `"70" marker + 2-byte capacity-ladder code pair + chip name (NUL-term) + fixed config block + CSV register script` — indexed by the plugin's capacity code (read via scaler register 0x85A on RTD 'I/H/N/P' families, or a 0x77 I2C byte on 'G/A/P'), **not** by JEDEC ID. Codes: A25L020=`12 11`, A25L040=`13 12`, A25L080=`14 13`, **A25L032M (ours)=`16 15`** (2/4/8/16/32-Mbit ladder); our flash IS in the table. A code mismatch falls back to the 'Default' record ("Flash MisMatch Use Default Value"), it does NOT abort. Grammar: `06,<reg>,<val>` = write reg; `0d,<reg>,<len>,…,<wait>` = read reg. Registers: **index `0x60`, data `0x61–0x66`, strobe pairs `0x20→0x21` and `0x38→0x39`**. No script contains `0x9F` — the JEDEC-0x1F gate remains OUR oracle (sound engineering, but the vendor keys on the capacity code + per-bank read-back instead). Full pipeline: `Facts.ISP_PIPELINE` + `re/f_ispsteps.txt`. PWM2SPI = Realtek pin-banged SPI master on PWM pads (inferred; zero public docs).
6. **RM control facts (615.x)**: `0x731341` (AUXCH_CTRL) flags `0x844` = CACHEABLE|ROUTE_TO_PHYSICAL|**PRIVILEGED(0x4)** → root suffices (`osIsAdministrator()`); `0x73137C` (bulk I2C) = dead from userland (0x23/0x1b). NV2080 I2C controls (`0x20800601/2/3`, structs 532/276 B verified) work for GPU-internal ports only — every DP/HDMI port number → `INVALID_ARGUMENT`.

## Address rule + wire format (user protocol, binding)

- Disassembly addresses are **8-bit**; Linux/AUX fields are **7-bit**: `0x44→0x22`, `0x41→0x20`, `0x6E/0x6F→0x37`, `0x94→0x4A`. Never put `0x44` in an AUX address field.
- All probes use **I2C-over-AUX** (not native): cmd nibble `0x4`=write+MOT, `0x5`=read+MOT; address field = 7-bit slave; length byte = N-1; **MOT held across chunks**; stop = **address-only request, same slave, MOT clear, length 0**. A native `0x8/0x9` ACK is a failed test even if it ACKs (that's the DPCD path).
- Retry policy: **≥200 tries or 2 s on DEFER, backoff 5–20 ms**, log every reply verb (ACK/NACK/DEFER/TIMEOUT) + the raw command sent. One 10-retry TIMEOUT is not a result.

## Dead ends — do NOT re-litigate on this box (all experimentally measured)

1. HDMI bare-metal i2c-dev probe of `0x22`/`0x20` (before/during/after ISP — no ACK; ISP entry itself works there).
2. USB-C as a data lane on this model (manual p.7: video-only; kernel shows Billboard only; the Realtek hubs on buses 10/11 are the **motherboard's**, enumerating at second 1.7 of boot). Comm.dll *does* carry a full USB backend (`GetUsbDevicePath`/`SendUsbPacket`/`SetNewRealtekUSBMode`) for other MSI models with populated Type-C upstream — future feature, not this unit.
3. Native-AUX hand-rolled I2C start/stop bit-stuffing (DP spec §2.7.6 + NVIDIA's own `dp_auxbus.h` split native vs i2c request types; no fallback encodes I2C inside native).
4. `I2C_RDWR` on DP i2c-dev (ENOTTY on NVIDIA) and repeated-start combined transfers (zeros).
5. NVAPI on Linux 615.x (NGX shim only; all QueryInterface IDs NULL).
6. NV2080 I2C controls with DP/HDMI port numbers.
7. `0x73137C` bulk I2C control (INVALID_CLIENT/PERMISSIONS under root).
8. Raw byte reads at `0x37` as a flash window (it's the DDC/CC packet FIFO — the early "MAG 341CQ X28 oracle hits" were cached-descriptor **false positives**, proven by address ladder).
9. `drm_dp_aux` chardev / `DRM_IOCTL_DP_AUX` on nvidia-drm.
10. More than two strobe polarities without a JEDEC match (we never got a contact to strobe).
11. **Spec Step 1 final verdict (commit `d1f5948`)**: patient I2C-mode probe of `0x22` via `0x731341` as root — **108 tries / 2.0 s: all TIMEOUT, zero DEFER/NACK/data**, while `0x50` and `0x37` ACK real data with the same control and framing in the same run (native DPCD0=`0x12` sanity passed). The 4090 open module will not emit I2C transactions to `0x22` on this sink. **Re-measured 2026-10-09 on 615.78.08: identical (109 tries / 2.0 s, 100% TIMEOUT; same-run controls ACK). Verdict stands on both .71 and .78. Exhaustive close, session 14k:** full 7-bit `0x03–0x77` ACK sweep over the kernel relay (first scan ever with zero i2c-dev allow-list bias): ACKs ONLY `0x30/0x37/0x4a/0x4b/0x50`, 112 addresses TIMEOUT, zero NACKs — `0x3B` (the `0x77` G/A/P-family detect slave) silent too, consistent with RTD2711 being a 0x85A-register-family chip. Nothing hidden by the old allow-list. **Fourth origin, session 14n:** the bulk-I2C control `0x73137C` — prime suspect for what NVAPI rides (256 B/txn, driver-side split + ACK-retry) — proven **ALIVE from kernel context** (userland's `0x23 INVALID_CLIENT` gate skipped exactly as the kill-switch analysis predicted: EDID 2×128 B reads byte-perfect in one call, branch slaves `0x30/0x4a/0x4b` ACK, plain-7-bit addr form, no address policy), yet `0x22` answers `NV_ERR_GENERIC` exactly like an unoccupied slave, both addr encodings, read and unlocked write. The "kernel privilege + NVAPI's likely control" hypothesis is **falsified honestly**: this sink refuses `0x22` on every Linux path, privileged or not; the Windows delta narrows to NVAPI's path/sequencing (open question #2) — and the experiment re-run is now one command (`python3 scratch/bulk_kernel_test.py`, seconds) for every future driver release.
12. **USB-ISP on this unit (user-verified 2026-10-10, session 15b)**: the X28's USB-C/upstream port is **display-only, no data path** — the vendor's Realtek/FTDI USB comm backends (`SetNewRealtekUSBMode`, `*FTDI*`, `TypeCUsb*` exports, the `rtd38/` family) cannot reach the scaler through the monitor's connector; those backends assume board-level ISP adapters. Reinforces open #8: recovery routes on this unit are service-channel or CH341A, not USB.
13. **DDC-ISP framing via NVIDIA, architecturally closed (session 15h)**: `I2C_RDWR` (the combined-START 2-message framing that flashrom's `mstarddc_spi` — the community's DDC-ISP protocol implementation — uses for every read) returns **ENOTTY at every address on NVIDIA's i2c-dev**, on both the DP-emu and analog-HDMI buses. Combined with the address-phase NACKs at 0x35/0x49 (both buses, ISP-magic-alive) and the absence of `mstarddc_spi` in this machine's flashrom build, the entire "community MSTAR dumper trick" is dead ON THIS GPU/DRIVER independent of any monitor behavior — consistent with every community success being amdgpu/i915. Also retired with evidence: `RMUseSwI2c/RMI2cSpeed` (class = basic-DDC-broken cards; ours never was; 2026-08 GSP-era sighting: accepted, zero effect — `Facts.PROTON_045` keeps the dormant-knob list). The clip route (`ch341a_spi`, present and USB-ready) is now the ONLY non-native-hardware-dependent path, and the borrowed-Windows 12%-observable the only free Windows datum.
14. **Standby-state automation is dead on this box (session 15j)** — the MStar-community flash recipe's precondition (boeglin 2014, upstream of flashrom mstarddc_spi: monitor ASLEEP + analog DDC) cannot be reached from any bus: DPMS-off leaves the scaler fully serving (NVIDIA keeps the AUX link trained; Xwayland `xrandr --off` even BadMatch-fails), blinding the input (VCP `0x60`→DP-2 verified empty, 151 s) keeps `0x37`/`0x50` ACKing with ISP magic unchanged, and VCP `0xD6` (power) is undeclared + silently ignored. **USER CORRECTION (post-15j): the power button = FULL OFF, not standby — standby is reached only by no-signal.** That retroactively reframes the input-blind runs: they were already probing the standby region, and there `0x37`/`0x50` provably stay answering while `0x35` stays silent — i.e. the MStar 'asleep opens 0x49/0x59' behavior does NOT reproduce on this RTD unit. Cell (B) powered-OFF is CLOSED negative (15k, content-verified: i2c-dev EIO, nothing answers at content level; and the phantom-ACK window found both OFF *and* post-power-on). Cell (A) = visual-confirm standby sweep stays queued — polish-grade only, the state's bus behavior is already measured. Bonus negative from the same session: the CpIspTool initial pair `[0x85,0xA0]` ROUTES to the DDCCI-ISP mailbox (valid-empty `6e 80 be`, idempotent — the ONLY non-zero-reply writes ever seen on `0x37`) but **opens no flash lane** from FW.009.
